# Crafted NAND title directories can exhaust Android heap during DSiWare checks

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_b3ec145f5094e12cfd0ad76e` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `medium` · layer `app`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** Cap, deduplicate and page DSi title enumeration before creating Java objects. A configured NAND is accepted without a size/title-count policy, the native mount appends every matching raw directory entry, and JNI eagerly allocates a 4096-byte icon plus strings and an object for every result.
- **Attack path:** An attacker convinces a user to configure a mountable DSi NAND whose title directory contains a very large number of valid-looking, potentially duplicate entries. Opening the manager or checking a DSiWare launch builds a retained Java record and 4 KiB icon for every entry until work or heap is exhausted.
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Independent source-backed amplification analysis from configuration acceptance through FAT enumeration, JNI allocation and Android manager/launch consumers; Configuration validation does not bound NAND size or structure; Any provider-backed file called nand.bin passes this configuration check; no length or… Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** A usable malicious image must mount and contain at least one resolvable title.tmd and &gt;=0x4000 app path. Configuration is user-mediated; there is no remote automatic NAND replacement path.
- **Limitations:** Device heap limits and document-provider file behavior determine the practical count needed for termination.
- **Recommended correction:** Validate NAND length against supported formats, impose a conservative maximum raw directory-entry and unique-title count, reject duplicate title IDs, check every f_readdir result, and stop before per-record parsing when the budget is exceeded.
