# A restored zero SPU interval can trap the emulator thread at one timestamp

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_6422719eff0c108a08550a57` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `medium` · layer `core`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** SPU savestate loading accepts any MixInterval although runtime configuration produces only 704 or 1024. If a crafted state restores zero while the valid SPU event remains scheduled, the callback requeues the periodic event at the same timestamp, so RunFrame repeatedly dispatches it without scanline progress.
- **Attack path:** Not separately specified in the sealed finding.

Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. - **Recommended correction:** Reject restored MixInterval values outside the supported positive set, or reconstruct the interval from the selected sample rate instead of serializing it. Additionally reject periodic scheduling with delay &lt;= 0 and fail the state load transactionally.
