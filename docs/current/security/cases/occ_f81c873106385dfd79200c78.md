# Guest-triggered rumble events enter an effectively unbounded Android SharedFlow

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_f81c873106385dfd79200c78` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `medium` · layer `core`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** The native Rumble Pak emits stop/start events whenever a guest alternates its value. Android's first-stage emulator event flow accepts Int.MAX_VALUE buffered elements and is consumed on the main dispatcher, so sustained producer/consumer imbalance can retain an attacker-controlled number of event objects even though the downstream rumble flow is correctly bounded.
- **Attack path:** guest ROM writes -&gt; native stop/start messages -&gt; HandlerThread -&gt; Int.MAX SharedFlow buffer -&gt; main collector
- **Evidence and proof level:** **static** in the sealed finding (`status not specified`): static source trace; Guest writes emit two events per value change; A malicious ROM can alternate values to generate a sustained event stream. Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** The native pipe is bounded and blocking. The main consumer performs little work.
- **Limitations:** No dynamic stress test was authorized, so time-to-OOM remains unmeasured.
- **Recommended correction:** Represent rumble as conflated state or use a small bounded manager flow with DROP_OLDEST; coalesce redundant stop/start pairs before JNI.
