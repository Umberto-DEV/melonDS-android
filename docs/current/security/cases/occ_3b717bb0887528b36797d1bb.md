# Loading a crafted DSi savestate can trap AES processing in billions of iterations

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_3b717bb0887528b36797d1bb` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `low` · layer `app`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** The AES state loader restores an unrestricted mode and remaining-block counter. For a mode above three, the processing switch consumes no FIFO data, but the surrounding loop still decrements an attacker-selected 32-bit block count, allowing roughly 4.3 billion tight iterations after the guest triggers an update.
- **Attack path:** state mode/counter -&gt; AES update loop -&gt; CPU exhaustion
- **Evidence and proof level:** **static** in the sealed finding (`validated`): static source trace; Mode and remaining work are restored without semantic checks; A validly framed FIFO can coexist with an invalid mode and maximum work counter. Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** Normal MMIO cannot set invalid mode. Follow-on guest access is required.
- **Limitations:** Wall-clock hang duration was not benchmarked.
- **Recommended correction:** Reject states with 'AESMode &gt; 3' and validate counter/FIFO/active-state coherence; add a default switch case that aborts processing, resets work, and marks the state invalid.
