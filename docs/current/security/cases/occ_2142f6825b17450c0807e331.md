# Importing a wrong-size DSiWare save can replace the installed title’s persistent data

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_2142f6825b17450c0807e331` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `medium` · layer `app`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** The Android DSiWare manager already has the installed title's public/private save sizes and banner flag, but its picker forwards only title ID, file type, and provider URI. JNI and the shared core then copy every byte reported by the provider into a staged file and atomically publish it as public.sav, private.sav, or banner.sav without comparing the source length to the title header.
- **Attack path:** Provider URI -&gt; Android DSiWare import -&gt; JNI path -&gt; full-length staged copy -&gt; live title-data rename
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Offline Android-to-JNI-to-core source trace with desktop code used only as expected-control comparison; Android already models installed title-data sizes; The Android domain object carries the exact public/private sizes and the banner-save presence flag, so the import boundary has enough metadata to select… Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** The user explicitly selects a file for import. Staging and backup preserve the old file when copy or rename fails.
- **Limitations:** Static validation only; the malformed save was not imported or executed under the read-only constraint. No large sparse document or hostile ContentProvider was executed.
- **Recommended correction:** Enforce the invariant inside 'NANDMount::ImportTitleData': derive the expected public/private size from the installed title header and use the fixed banner-save size, obtain a non-truncated 'u64' source length, reject any mismatch before creating the staged file, and abort if the provider's size changes while copying.
