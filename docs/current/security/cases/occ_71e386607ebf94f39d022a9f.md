# A 32-bit URI hash lets one compressed ROM substitute another cached ROM

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED`.

- **Identity and status:** `occ_71e386607ebf94f39d022a9f` · scan `4c41e000-6ba0-4453-aaa7-3cdbec542687` · severity `medium` · layer `app`. Technical disposition from CSV: CORRECTED. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** Extracted ROMs are named and looked up solely with 'rom.uri.hashCode().toString()'. No original URI or digest is stored or verified, so an attacker-controlled provider can choose a colliding URI, populate the key first, and cause a later victim ZIP/7z launch to consume the attacker's extracted bytes.
- **Attack path:** Chosen provider URI -&gt; 32-bit hash key -&gt; attacker extraction -&gt; later victim hash lookup -&gt; attacker bytes
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Independent static source trace; Hash-only lookup; No URI or content metadata is checked on hit. Disposition evidence: **recorded dynamic post-fix checks**; pre-fix evidence remains static unless the report records an explicit RED — distinct URI key and atomic publication tests pass. No dynamic RED is inferred unless the report records it explicitly.
- **Counterevidence:** Attacker must know/guess target URI and win the cache-population timing. Only compressed ROMs use this cache.
- **Limitations:** No archive, cache-collision, or heap-exhaustion proof of concept was executed.
- **Recommended correction:** Use a collision-resistant digest such as SHA-256 over a canonical source identity and store sidecar/database metadata with the exact original URI/document identity. Verify metadata on every hit and use atomic per-ROM temporary files.
