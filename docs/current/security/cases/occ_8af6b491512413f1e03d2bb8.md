# Guest DNS queries leak native resolver allocations

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED`.

- **Identity and status:** `occ_8af6b491512413f1e03d2bb8` · scan `4c41e000-6ba0-4453-aaa7-3cdbec542687` · severity `medium` · layer `core`. Technical disposition from CSV: CORRECTED. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** For every successful non-overridden guest DNS query, HandleDNSFrame calls getaddrinfo, reads the first result, and never calls freeaddrinfo. Because Android always installs Net_Slirp and a ROM controls guest DNS traffic, repeated valid queries can accumulate native heap allocations until the emulator is terminated.
- **Attack path:** Guest names drive getaddrinfo allocations whose owner is lost.
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Static allocation/lifetime tracing plus Android driver reachability.; Affected driver is Android-reachable; Each Android emulator configuration installs Net_Slirp. Disposition evidence: **recorded dynamic post-fix checks**; pre-fix evidence remains static unless the report records an explicit RED — DNS suite passes with scoped freeaddrinfo ownership. No dynamic RED is inferred unless the report records it explicitly.
- **Counterevidence:** Overrides and failed lookups avoid the leak. Only one DNS question is processed per packet.
- **Limitations:** Allocation size and exact queries-to-OOM vary by Android resolver implementation and available heap. Heap growth rate was not measured.
- **Recommended correction:** Wrap addrinfo* in an RAII owner with a freeaddrinfo deleter, or call freeaddrinfo on every successful path after copying the selected address. Add request throttling only as defense in depth, not as a substitute for correct ownership.
