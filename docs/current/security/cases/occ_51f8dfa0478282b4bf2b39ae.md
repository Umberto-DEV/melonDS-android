# ROM padding exposes uninitialized native heap bytes to emulated cartridges

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED_SECOND_SCAN`.

- **Identity and status:** `occ_51f8dfa0478282b4bf2b39ae` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `high` · layer `core`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** For a non-power-of-two NDS or GBA image, both 'PadToPowerOf2()' overloads allocate the next power-of-two byte array and copy only the logical file length, despite their documented zero-padding contract. Cartridge construction then publishes the larger allocation as 'ROMLength', and guest-controlled NDS/GBA cartridge reads deliberately accept or mirror addresses throughout that padded range.
- **Attack path:** Selected non-power-of-two ROM -&gt; exact-length Android buffer -&gt; uninitialized power-of-two core allocation -&gt; padded size stored as ROMLength -&gt; malicious guest cartridge read -&gt; stale native bytes returned to guest.
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Static source trace from Android file read through padding, cartridge length commit, and guest-visible NDS/GBA read implementations.; Padding API promises zeroes; Callers and reviewers may rely on a deterministic zero tail, but the implementation does not establish it. Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** All reads stay within the allocated object. Fresh OS-backed pages may happen to contain zeroes.
- **Limitations:** No allocator-grooming or Android disclosure proof was executed. The exact leaked bytes depend on allocator reuse and object size.
- **Recommended correction:** Value-initialize every padded allocation ('new u8[newlen]()' or an explicit 'memset(newdata.get()+len,0,newlen-len)') before publishing it. Preserve logical content length separately from allocation/mirroring size and ensure guest reads beyond logical bytes return deterministic hardware-appropriate fill. Add allocator-reuse tests for both overloads and NDS/GBA guest reads.
