# A tiny cheat database can request a near-2 GiB allocation

[Security index](../README.md) · [Disposition register](../FINDINGS.csv)

**Canonical disposition:** `CORRECTED`.

- **Identity and status:** `occ_bc26e0f9273443d666f51fd1` · scan `4c41e000-6ba0-4453-aaa7-3cdbec542687` · severity `medium` · layer `app`. Technical disposition from CSV: CORRECTED. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** 'UsrCheatDatabaseParser' trusts signed offsets from the R4 DAT address book, sorts them, and uses the gap to the next entry as the allocation size for every nonfinal game. A 304-byte file can place entries at '0x130' and '0x7ffffff0', producing a first block size of 2,147,483,328 bytes.
- **Attack path:** DAT address book -&gt; sorted offsets -&gt; gap arithmetic -&gt; ByteArray
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Static exact-payload arithmetic and exception-flow validation; Adjacent untrusted offsets define nonfinal block sizes; Only the last entry gets the 1 MiB cap. Earlier attacker-controlled offset gaps flow directly to allocation. Disposition evidence: **recorded dynamic post-fix checks**; pre-fix evidence remains static unless the report records an explicit RED — allocation/code cap tests pass. No dynamic RED is inferred unless the report records it explicitly.
- **Counterevidence:** Fixed worker/channel counts bound concurrency, not an individual allocation. Room replacement is transactional, reducing partial database corruption.
- **Limitations:** The OOM payload was not executed. Android heap limits determine the exact failure mode.
- **Recommended correction:** Validate every offset as nonnegative, monotonic, within the known descriptor/file length when available, and within a strict per-game maximum. Use checked subtraction. For unknown-length streams, incrementally read into bounded storage instead of allocating the advertised gap.
