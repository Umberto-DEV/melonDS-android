# Verify every Gradle artifact before privileged release builds

- **Identity and status:** `occ_44c82f1de1a141fb56634019` · scan `ab26b107-97dd-4557-9c4b-2942e5df879d` · severity `low` · layer `app`. Technical disposition from CSV: CORRECTED_SECOND_SCAN. The Security UI state may remain **Open**; it is separate from the technical disposition.
- **Summary:** Release workflows resolve executable Gradle plugins and dependencies from Google, Maven Central, the Plugin Portal and JitPack without committed dependency-verification metadata or lock state. The jobs materialize signing secrets before Gradle configuration/resolution, so a substituted artifact can execute with release authority.
- **Attack path:** Repository response -&gt; Gradle resolution -&gt; configuration/build execution -&gt; signing files/secrets and signed APK.
- **Evidence and proof level:** **static** in the sealed finding (`validated`): Static workflow/Gradle configuration review.; Remote plugin and dependency repositories include JitPack; Version coordinates are pinned, but no repository-local artifact digest is enforced for resolved plugin/dependency bytes. Disposition evidence: **recorded post-fix class/suite tests, without an individual dynamic reproduction of the trigger** — Focused regression plus final host/JVM/NDK/ART checks recorded in the second-campaign report. This card is supported by source analysis unless it cites a specific RED/GREEN result; aggregate final checks are not counted as an individual finding GREEN.
- **Counterevidence:** Actions use full commit SHAs. Gradle distribution has SHA-256.
- **Limitations:** External repository immutability and runner cache policy are unknown.
- **Recommended correction:** Commit strict Gradle dependency-verification metadata for all plugins/dependencies; enable dependency locking; minimize JitPack; resolve/build without release credentials and pass verified outputs to separate signing/publishing.
